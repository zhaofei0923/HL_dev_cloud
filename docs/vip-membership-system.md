# VIP会员与人工牵线体系

本文说明会员实现、发布门禁和服务规则。代码与本地测试通过只证明本地逻辑；云端部署、商户权限和真实付款应分别以对应的验收证据为准。套餐展示与正式收款分别控制。

## 产品与价格

“我的特权”提供“VIP会员”和“人工牵线”两个页签。在线会员统一一档VIP，不设置SVIP。人工牵线是独立购买的服务，不自动赠送VIP，也不因VIP到期抹除已建立的正式配对关系。

| 产品 | 套餐代码 | 价格（元） | 服务期限 | 牵线次数 |
| --- | --- | ---: | ---: | ---: |
| VIP周卡 | `vip_week` | 61.60 | 7天 | 不适用 |
| VIP月卡 | `vip_month` | 198.00 | 30天 | 不适用 |
| VIP季卡 | `vip_quarter` | 398.00 | 90天 | 不适用 |
| VIP年卡 | `vip_year` | 698.00 | 365天 | 不适用 |
| 人工牵线单次 | `matchmaking_single` | 2,980.00 | 30天 | 1次 |
| 人工牵线1个月 | `matchmaking_month_3` | 6,980.00 | 30天 | 3次 |

期限按固定天数计算。两档人工牵线均由付款经服务端确认后开始30天计期，提供专属红娘1对1对接；这里的“线下”仅指专属对接，交易与正式建联仍在小程序内完成，使用虚拟支付。所有金额由服务端目录生成，订单以分存储；客户端不能提交价格、有效期或次数覆盖服务端快照。约每日价格只用于VIP展示，不作为扣款单位。套餐一次性付款，到期手动续费，不自动扣款。

2026-10-13新目录使用两个新商品ID。旧 `matchmaking_month`（30天2次）、`matchmaking_quarter`（90天8次）、`matchmaking_halfyear`（180天16次）无论目录门禁状态或数据库旧配置是否active，均不再展示出售或创建新单，旧未付款单不再签发新支付尝试。原订单继续查单、处理可信迟到付款和退款；已购套餐保留原价、期限、次数，不转换为新套餐，也不直接释放未完成付款占位。

保留11项VIP权益：无限畅聊、交换微信、无限划卡、高级筛选、上线提醒、专属客服、专属会员标识、谁喜欢我、查看来访、隐身访问、查看专区。聊天仍需要双方互相喜欢或已建立正式服务/配对关系；微信号必须双方同意后才向对方展示。上线提醒是站内通知，不承诺微信后台推送。隐身访问与关闭资料展示是不同设置。截图中划除的营销权益和人工牵线红圈内的营销权益不纳入本版。

## 发布与付款门禁

三个相关门禁各自独立。其中目录门禁和人工收款门禁为本版新增；VIP支付总门禁沿用原有设置。

| 配置 | 未配置或为false | 配置为true |
| --- | --- | --- |
| `VIP_MEMBERSHIP_CATALOG_READY` | 有非退役历史目录时继续使用历史目录；无历史目录时展示当前6个套餐但默认不可购买 | 切换新目录，仍需商品状态、支付配置和购买准备条件均通过；旧三人工商品始终停售 |
| `PAYMENT_INTEGRATION_READY` | VIP不开放新付款；保留已配置的历史查单能力 | 仅允许使用配置完整、权限有效的VIP虚拟支付能力 |
| `MATCHMAKING_PAYMENT_READY` | 人工牵线新付款关闭；默认不继承VIP付款门禁 | 独立检查虚拟支付配置、资料完整、当前主理人归属和主理人准备确认后允许购买 |

目录门禁不是支付权限证明。VIP与人工牵线的新订单统一走微信虚拟支付，需在平台配置当前6个道具。套餐代码必须与平台 `productId` 一致，金额必须与服务端快照一致：

| 道具ID | 金额（分） |
| --- | ---: |
| `vip_week` | 6160 |
| `vip_month` | 19800 |
| `vip_quarter` | 39800 |
| `vip_year` | 69800 |
| `matchmaking_single` | 298000 |
| `matchmaking_month_3` | 698000 |

两类商品共享Offer ID、环境和对应AppKey，购买门禁仍各自独立。开通前核对AppID、商品审核、当前环境、回调及查单能力。当前两档牵线价格低于用户报告的后台道具1万元上限，商品审核和实际可购买性仍需平台验证；前端iOS付款入口仍未开放。代码允许签名不代表平台已接受商品。微信团队[虚拟支付业务运营指南](https://developers.weixin.qq.com/community/minihome/doc/00002cf077cd4810fee42f4b865c01)将在线相亲社交列入虚拟服务；本项目人工牵线按在线推荐、双方确认和小程序内正式建联交付。

VIP与人工牵线均使用 `requestVirtualPayment`，配置缺项、iOS不支持或平台受限时均不回退到JSAPI。每笔订单保存不可切换的支付通道、环境及Offer ID快照。历史JSAPI订单只通过原普通微信支付桥接查单、处理可信迟到付款及退款，不重新打开旧收银台，也不转换成虚拟订单再次付款。概览返回旧订单的原通道查询配置，恢复人工订单时界面切回人工牵线页签。

未绑定主理人的用户可以购买VIP。人工牵线需资料完整、存在有效且已认证的当前主理人关系，并由该主理人确认服务准备情况。资料版本或主理人归属发生变化后，需要重新核验准备状态；确认服务准备不等于替会员接受具体牵线。

沿用原支付安全边界：待处理订单先查单；取消支付不是未付款证明；微信原生成功回调不是履约证明；订单、账号、金额、道具及付款尝试编号必须核验；未最终确认不得新建重复扣款；已付款但关系异常时进入人工复核。商户受限保留查单入口，禁止反复拉起支付。

## 权益数据与历史兼容

以下集合属于服务端保护数据，禁止小程序直接读写，也禁止通用CMS集合编辑、导入或删除。只能通过带有身份和权限校验的 `hlApi` 专用路由处理。

- `hl_vip_entitlements`
- `hl_matchmaking_packages`
- `hl_matchmaking_requests`
- `hl_matchmaking_readiness`
- `hl_member_visits`
- `hl_member_privacy`
- `hl_wechat_exchanges`
- `hl_online_subscriptions`
- `hl_member_presence`

发布前需在云环境确认这些集合的客户端安全规则拒绝直接访问，并确认CMS保护名单生效。代码中的路由鉴权不能代替云数据库客户端安全规则。列表和详情只返回必要的公开投影，微信号只在双方同意后的交换详情中出现；隐身访问不返回会泄露隐身状态的信息。

新VIP权益按用户独立记录，不以主理人归属作为在线VIP的唯一依据。读取新记录之前，服务端兼容有效历史付费会员/VIP：沿用其最晚有效期，历史长期有效权益保持长期有效。该读取兼容过程不批量写回历史档案。首次新VIP履约时在受控事务中保存历史基线与订单权益记录。

VIP续费从“当前有效期”与“本次服务端确认时间”较晚者开始延期；已过期权益从本次确认时间重新计算。每个订单只发放一次。长期权益不会因短期套餐缩短。售后调整按具体订单的权益账本重算，保留其他正常订单及历史基线，不直接覆盖整个会员有效期。

人工牵线每笔订单生成独立套餐，记录开始时间、到期时间、总次数、已使用次数和剩余次数。新增套餐不修改其他套餐的有效期，不能把VIP续费天数折算为牵线次数。已过期、已用完或已退款套餐不能继续履约。

## 人工牵线与售后流程

1. 会员完善档案、绑定主理人；主理人检查资料并在本人所属会员页面确认服务准备状态。
2. 购买人工套餐，服务端确认付款后发放独立服务包。
3. 会员在合适对象资料页提交牵线申请，进入“待主理人审核”；当前主理人通过专用 `approve` 路由审核。主理人直接推荐的申请可进入双方确认阶段。主理人审核只确认服务安排，不代替任何一方同意。
4. 双方分别接受后，服务端重新核验账号、公开资料、当前主理人关系、套餐期限和次数，在同一事务中建立正式配对并扣减一次。优先使用最早到期且仍有余量的套餐。重复点击或重复回调不重复扣次。
5. 审核前或只有单方接受时不扣次；拒绝、取消不扣次。没有有效剩余次数、套餐到期或归属变化时阻断建联并保留可核查记录。
6. 已建立的正式配对按现有服务关系提供沟通；不能通过取消旧申请反复恢复次数或抹除履约记录。

错误扣次由主理人受理并提交售后审核；管理员通过 `POST /admin/matchmaking/requests/{requestId}/restore`，填写 `caseId` 和 `reason`，每份已建联请求最多恢复一次原套餐次数。接口只接受管理员凭证，保留原建联记录、审核人、审核理由和案件编号；重复同案件不再加次，其他案件不能重复恢复。原套餐到期日不延长，已退款套餐禁止恢复，其他套餐不受影响。

退款由受控商户/管理员流程核查，不提供客户端自改退款状态或余额入口。确认退款后，VIP撤回对应订单尚未使用的期限并保留其他订单；人工套餐撤回未使用次数，保留已履约次数和正式配对历史。涉及已履约服务的退款金额、争议或人工补偿需售后核查，不能仅凭页面取消动作自动退款。

历史JSAPI退款回调只定位退款单，原桥接服务重新查退款及原支付订单，核对签名、身份、币种、原交易和全额金额，再等待权益处理成功后应答。VIP与人工牵线的虚拟支付退款推送同样仅作触发器；重新查原支付单，要求退款完成、原金额和交易一致、平台剩余可退款金额 `left_fee` 为数值0。缺少完整金额凭据或部分退款时保留权益并进入人工复核，不接受推送体自行声明的金额。已退款订单不返回付款成功状态。两套契约分别校验订单原通道，不能交叉发放或撤回权益。

## 本地验收与上线证据

本地重点覆盖：当前6个套餐的准确金额/期限/次数、旧三人工商品在各目录状态下均不可新购、旧订单按快照查单/迟到履约/退款；VIP未绑定主理人购买；人工准备确认与资料变更；本人申请/主理人审核/双方接受；次数不足和过期拒绝；并发与重复确认只扣一次；旧会员和长期权益兼容；退款不影响其他订单；非VIP无法绕过高级筛选和专区权限；隐身、来访与微信号不泄露；账户切换和原订单恢复。

前端专项回归同时覆盖两类商品的虚拟支付参数核验、禁止JSAPI回退、历史JSAPI订单按原通道查询且禁止续付、支付取消先查单、临时查询失败有界重试、商户受限和已付款待复核。本地界面预览与模拟测试不代替微信开发者工具、真机体验和受控端到端支付验收。
